## 1. Выбор стека

Бриф предлагает: Python + FastAPI, PostgreSQL, фронт — на выбор разработчика
(«выбираем тот вариант, на котором разработчик быстрее соберёт оба кабинета»).

| Слой | Выбор | Почему |
|---|---|---|
| Backend | Python 3.13 + FastAPI + Uvicorn | Основной вариант из брифа; быстрая разработка, OpenAPI из коробки (NFR-12) |
| ORM/БД | SQLAlchemy 2.0 (async) + asyncpg + PostgreSQL 16 | Асинхронный стек, строгие уникальности и FK для NFR-06 |
| Миграции | Alembic | Версионирование схемы, воспроизводимый запуск (NFR-11) |
| Валидация | Pydantic v2 | Схемы запросов/ответов, разграничение публичной проекции (NFR-01) |
| Пароли | Argon2id (`argon2-cffi`) | Требование NFR-02 |
| Сессии | JWT (access, httpOnly cookie + Bearer), PyJWT | Подходит под NFR-02 (cookie HttpOnly/SameSite); CSRF-защита изменяющих запросов |
| Email | SMTP; в dev — перехватчик (печать в лог) | FR-02; локальный перехватчик допустим для разработки |
| Frontend | React 18 + TypeScript + Vite + React Router | Наиболее привычный вариант, быстро собираются два кабинета |
| Запуск | Docker Compose (db, api, web) | NFR-11: «Предлагаем Docker Compose для приложения и БД» |

Решение зафиксировано в `backend/pyproject.toml` / `frontend/package.json` (версии закреплены).

## 2. Первый результат (текущая итерация)

Задача №1 этапа «Основа» из Requirements (строки 937–939):

> Репозиторий, БД, миграции, запуск, роли, email, собственный профиль и компания.
> FR-01–05, 16; базовая защита сразу.

Что уже покрыто в этой итерации:
- репозиторий, docker-compose, миграции, seed справочников, README;
- регистрация с ролью `candidate`/`employer`, согласием (FR-01), подтверждение email (FR-02);
- вход/выход, сессии, права по ролям и владельцу (FR-03);
- каркасы профиля кандидата (FR-05) и компании работодателя (FR-16) с сохранением;
- единый формат ошибок Problem Details RFC 9457 с классами E01–E20 (каталог ошибок, ER-01, FR-30);
- два кабинета во фронтенде.

## 3. Вопросы по брифу

### 3.1. Вопросы к заказчику/организаторам (из брифа, раздел «Уточнения заказчику»)
1. Допустимы ли для демонстрации две специализации и два грейда (4 категории) и одна активная категория на кандидата?
2. Как трактовать ограничение смены грейда после первого неуспешного теста и после успешного прохождения теста выше?
3. Какой объём пилотной проверки вариантов заданий ожидают эксперты для обоснования сопоставимой сложности?
4. Каковы точные сроки промежуточной и финальной сдачи, длительность демо и способ предоставления доступа экспертам?

### 3.2. Вопросы команде (решаем без остановки технического старта)
5. Подтверждаем ли направления Python backend и системный анализ и пороги D-02–D-06 (6 заданий/20 мин, 70%/50%, 24 ч / 90 дней)?
6. Какой способ отправки email используем для демонстрации: реальный SMTP на контрольный адрес или локальный перехватчик (Mailpit/MailHog)? В dev кладём перехватчик.
7. Точные тексты согласий (версия 1.0) и порядок их отображения при регистрации.
8. Какие задания аналитик готовит первыми — какой грейд/специализация закрывают «первый полный путь» (этап 2)?

### 3.3. Мои предложения (по умолчанию до уточнений)
- D-01: Python backend + системный анализ, Junior + Middle, одна активная категория.
- D-02–D-06: значения из Requirements берём как рабочие; они в конфигурации.
- Email: в dev-окружении письмо печатается в лог API и сохраняется ссылка подтверждения; в compose поднимем Mailpit.
- Разделение ФИО: по каталогу ошибок поле `full_name` единое (2–150 символов), форму не делим.
